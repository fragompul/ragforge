# The HNSW recall bug that unit tests could not see

*How a "correct" index silently lost documents, how the benchmark caught it, and the three changes that fixed it.*

RagForge's HNSW index passed every test I wrote for it and still returned wrong answers in
production-shaped workloads. This is the story of finding out why, because the failure mode is
generic to any graph index with deletions and filters.

## Symptom

Recall@10 against exact search looked fine on random data (0.99) but collapsed in two situations:

1. **Filtered search** — asking for the top 10 documents *from one tenant* returned fewer than 10
   results, or none, even though plenty existed.
2. **Duplicate floods** — ingesting many near-identical chunks (boilerplate repeated across pages)
   made some documents *unreachable*: no query could ever return them.

## Cause

* **Over-fetch-then-filter.** The old filter path searched for `k × factor` neighbours and dropped
  the ones that failed the predicate. With a selective filter the surviving set is empty no matter
  the factor.
* **Pruned edges.** HNSW's neighbour-selection heuristic drops a candidate that is closer to an
  already-selected neighbour than to the query. With many duplicates, a new node can be pruned out
  of *every* neighbour list, leaving it with no inbound edges.

## Fix

1. **Filter inside the traversal.** The predicate is evaluated while walking the graph: filtered-out
   nodes still guide the walk but never enter the result set. If the walk exceeds a visit budget the
   index falls back to an exact scan of the matching rows (provenance `vector:hnsw+scan`), so a
   selective filter degrades to correct-but-slower rather than wrong.
2. **A pinned reachability backbone.** Every node keeps one *pinned* edge from its insertion-time
   parent that pruning may never remove, so every node stays reachable from the entry point.
   `unreachable()` verifies it, and the robustness tests assert it after floods and deletions.
3. **Tombstones through the same predicate**, rather than widening `ef`, plus `compact()` to
   physically rebuild once too many nodes are dead.

## What I would tell my past self

* Test the *invariants* of a data structure (every live node reachable; filtered recall equals exact
  recall), not just example queries.
* Property-based tests and a benchmark that sweeps the awkward regimes (selective filters, duplicates,
  heavy deletion) found in minutes what example-based tests never would.
